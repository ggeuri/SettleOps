# Flyway Migration Policy (Immutable Rule)

## 목적
- DB 변경 이력을 **누적/재현 가능**하게 유지하기 위해 Flyway 마이그레이션 파일을 **불변(Immutable)** 으로 관리한다.
- Flyway는 적용된 파일 내용이 바뀌면 **checksum mismatch**로 재현성이 깨지므로, “한 번 공유/적용된 파일은 절대 수정하지 않는다”를 원칙으로 한다.

## 핵심 규칙 (Immutable)
1. **이미 공유되었거나 적용된 버전 파일은 절대 수정하지 않는다.**
   - DDL/데이터/주석/공백/정렬 포함. *(checksum mismatch 방지)*
2. 변경이 필요하면 **반드시 신규 버전 파일을 추가한다.**
   - 예: `V3__*.sql`, `V4__*.sql`, `V100__*.sql` 등

## LOCKED CORE 범위
- `V1__*.sql`, `V2__*.sql`, `V99__*.sql` 은 **LOCKED CORE**로 간주한다.
- 해당 파일은 내용 수정/재정렬/주석 변경 포함 **일체 수정 금지**.

> NOTE: 이미 공유/적용된 파일은 LOCKED CORE 여부와 무관하게 “수정 금지”가 기본 원칙이다.
> LOCKED CORE는 특히 더 강하게 리뷰에서 반려한다.

## 변경이 필요할 때의 처리 방식
- 스키마 변경(컬럼/인덱스/제약 등): 다음 버전으로 `V{N+1}__describe_change.sql` 신규 추가
- FK/CHECK 강화: 통합 직전 파일(예: `V99__fk_on.sql`)에서만 수행 *(기존 버전 수정 금지)*
- Seed/테스트 데이터:
  - **기존 버전에 seed가 이미 포함돼 있어도, 분리를 위해 과거 파일을 수정/이동하지 않는다.**
  - 이후부터는 스키마 DDL과 분리하여 `V{N}__seed_*.sql` 형태로 **신규 버전 추가**로 관리한다.

## 로컬 개발 환경 권장
- 마이그레이션이 꼬였거나 과거 seed 규칙이 바뀐 경우:
  - **로컬 DB drop 후 Flyway 재적용을 권장**
- 운영/공유 DB에서는 drop 금지(누적만 허용)

## 브랜치/PR 운영 가이드
- 문서 변경(PR)과 DB 마이그레이션(PR)은 **가능하면 분리**한다.
- 이유: 리뷰 범위 축소, 롤백/추적 용이성 확보

## 리뷰 체크(머지 조건)
- “기존 버전 수정”이 있으면 **무조건 반려**
- 신규 버전 추가 시:
  - 버전 번호 충돌 없음
  - 파일명 컨벤션(`V{N}__...sql`) 준수
  - 변경 사유/영향 범위를 PR 본문에 3줄 이내로 요약
