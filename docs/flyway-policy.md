# Flyway Migration Policy (Immutable Rule)

## 목적
- DB 변경 이력을 “누적/재현 가능”하게 유지하기 위해 Flyway 마이그레이션 파일을 불변(Immutable)으로 관리한다.

## 핵심 규칙 (Immutable)
1. **이미 공유되었거나 적용된 버전 파일은 절대 수정하지 않는다.**
    - 특히 LOCKED CORE로 지정된 파일은 변경 금지.
2. 변경이 필요하면 **반드시 신규 버전 파일을 추가한다.**
    - 예: `V3__*.sql`, `V4__*.sql`, `V100__*.sql` 등

## LOCKED CORE 범위
- `V2__*.sql`, `V99__*.sql` 은 **LOCKED CORE**로 간주한다.
- 해당 파일은 내용 수정/재정렬/주석 변경 포함 **일체 수정 금지**.

## 변경이 필요할 때의 처리 방식
- 스키마 변경: 다음 버전으로 `V{N+1}__describe_change.sql` 신규 추가
- FK/CHECK 강화: 통합 직전 파일(예: `V99__fk_on.sql`)에서만 수행
- Seed/테스트 데이터: 가능하면 스키마 DDL과 분리하여 `V{N}__seed_*.sql` 형태로 관리

## 로컬 개발 환경 권장
- 마이그레이션이 꼬였거나 과거 seed 규칙이 바뀐 경우:
    - **로컬 DB drop 후 Flyway 재적용을 권장**
- 운영/공유 DB에서는 drop 금지(누적만 허용)

## 브랜치/PR 운영 가이드
- 문서 변경(PR A)과 DB 마이그레이션(PR B)은 분리하는 것을 권장한다.
- 이유: 리뷰 범위 축소, 롤백/추적 용이성 확보.
